## Observed tool defects

Recorded, not filed — no issues opened for these.

1. **`combined_hook_exit_86` on the caller-supplied-object ConSan path.**
   `consan-tiny` and `consan-gemm` both end `overall_verdict=error`,
   `execution_status=error`, reason `combined_hook_exit_86`, with zero
   findings. Both drive ConSan through `consan_load.hip`, which `hipModuleLoad`s
   a prebuilt `.hsaco`. `consan-lds-dispatch` also supplies its own object and
   passes, so the failure follows the `consan_load` driver rather than the
   caller-supplied object idea in general. Reproducible, not a flake: the six
   archived survey reports show the same three errors.

2. **`Finding.kernel_name` and `Finding.entry_offset` are never populated.**
   0 of 160 findings carry either, on both sanitizers. `code_object`,
   `severity` and `code` are populated on all 160. Kernel attribution is still
   recoverable, but one level up — `kernel_results[].identity.name` and
   `backend.selected_kernel` — so attribution is per-scenario, not per-finding.

3. **ConSan's `code` is not a vocabulary.** Every ConSan finding carries
   `code = "1"`, so the namespaced citation is `consan:1` for all of them. The
   discriminating fields are `severity` (`race`) and the metadata instruction
   pair. Waitcheck by contrast emits the symbolic `wait_hazard`. The corpus
   keeps `code` as the cited token to match `triage_reward`'s existing
   vocabulary and carries `severity` and `metadata` alongside it.
